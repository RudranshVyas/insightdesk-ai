# Evaluation sets

Files here are **hand-graded by a human**. Nothing in this directory may be
generated by a model and then reported as ground truth.

Only `*.template.jsonl` files are committed. The real graded sets are
gitignored along with the rest of `data/`, because they reference ticket ids
from a dataset that never enters git.

---

## `retrieval_queries.jsonl` — Phase 5, Tier 2

The only tier whose numbers may be quoted as retrieval quality. Target 30–50
queries.

One JSON object per line:

```json
{
  "query_id": "Q001",
  "text": "Customer was charged twice for the same invoice and wants the duplicate refunded",
  "product_area": "Payments",
  "issue_type": null,
  "relevance": {"T0002": 2, "T0117": 1, "T0451": 0},
  "notes": "T0451 is a refund case but for a cancelled subscription, not a duplicate charge"
}
```

| Field | Meaning |
|---|---|
| `query_id` | Unique. **Must not** be a corpus `ticket_id` — a query that can retrieve itself measures nothing. |
| `text` | The analyst's problem description. Write it the way a real analyst would, not by copying a corpus ticket verbatim. |
| `product_area`, `issue_type` | Optional metadata filters. `null` when the analyst would not know them. |
| `relevance` | `ticket_id` → grade. |
| `notes` | Why you graded it that way. Future-you will not remember. |

### Grading scale

| Grade | Meaning |
|---|---|
| `2` | Directly resolves this problem. An analyst reading this case would know what to do. |
| `1` | Related and useful context, but not the answer. |
| `0` | Judged and **not** relevant. Recording a zero is information — it says you looked. |

A ticket you never looked at is simply absent. Absent ≠ 0.

### Rules the validator enforces

- `query_id` must not appear in the corpus.
- Every graded `ticket_id` must exist in the corpus.
- No duplicate `query_id`.
- A warning fires if every relevant ticket for a query sits in one MinHash
  template group — such a query rewards duplicate retrieval, not relevance.

### Building the set honestly

1. Pick queries **before** looking at what retrieval returns. Otherwise you are
   grading the system's own output and the metric is circular.
2. Grade a pooled candidate set from *all four* configs, not just the hybrid.
   Grading only the shipped config guarantees it wins.
3. Cover the boring cases, not just the interesting ones. A set made of hard
   queries understates the system; a set made of easy ones oversells it.
4. Include a few queries with **no** good answer in the corpus. Those test
   abstention, which is Phase 6's job.

Run it:

```bash
python -m backend.scripts.eval_retrieval
```

Then rebuild the manifest so `retrieval.evaluation_status` updates:

```bash
python -m backend.scripts.build_capabilities
```
